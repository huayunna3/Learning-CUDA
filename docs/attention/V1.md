# FlashAttention V1：正确性基线版

## 1. 这一版解决了什么

仓库原始的 `flashAttention(...)` 只有一行占位注释：

```cpp
// TODO: Implement the flash attention function
```

V1 的目标不是跑得快，而是先把下面三件事做对：

1. 三种张量布局和 GQA 分组下标正确；
2. causal mask 的边界正确；
3. 数值结果与测试参考实现逐位一致，给后面的优化版留一个可靠的“标尺”。

## 2. 公式与张量布局

输入张量采用 `[B, S, H, D]` 布局：

- `Q`: `[B, T, Hq, D]`
- `K`, `V`: `[B, S, Hkv, D]`
- `O`: `[B, T, Hq, D]`

对第 `b` 个 batch、第 `hq` 个 query head 的第 `i` 行：

```text
score[i, j] = dot(Q[b, i, hq, :], K[b, j, hkv, :]) / sqrt(D)
```

GQA 中多个 query head 共享一个 KV head：

```text
group_size = Hq / Hkv
hkv        = hq / group_size
```

causal 模式采用左上角对齐语义，第 `i` 行只能看到 `j <= i`：

```text
key_end = min(S, i + 1)
```

softmax 使用数值稳定的形式：

```text
m_i     = max_j score[i, j]
p[i, j] = exp(score[i, j] - m_i)
l_i     = sum_j p[i, j]
O[i, d] = sum_j (p[i, j] / l_i) * V[j, d]
```

V1 特意采用“先完整算出一行 softmax，再乘 V”的顺序，因为它与参考实现的浮点运算顺序一致。这样 float 测试的最大误差可以做到 `0`。

## 3. 实现结构

- Grid：`(T, Hq, B)`，一个 block 负责一个 query 行；
- Block：256 个线程；
- 共享内存：缓存 `Q` 一行、整行 `score/probability`、一个归约槽；
- 第一阶段：`threadIdx.x == 0` 串行遍历该行所有 key，求最大值；
- 第二阶段：仍由 0 号线程计算 `exp` 和分母，结果写入共享内存；
- 第三阶段：所有线程按 `d` 方向并行，完成 `P @ V` 并写回输出。

这里的“单线程算整行 score”看起来反直觉，但它是刻意保留的基线：它消除了归约竞争和求和顺序差异，确保先把正确性钉死。V1 的 NCU 报告也直接暴露了这个设计代价：平均每个 warp 只有 `1.90` 个活跃线程，`87.1%` 的指令间隔耗在 CTA barrier 等待上。

**修改前**


**修改后**

- `src/flash_attention_v1.cuh`：完整 V1 kernel 与 launcher；
- `src/flash_attention_common.cuh`：与参考实现对齐的 `expf_parts()`；
- `src/flash_attention.cuh`：版本选择与 host 端显存缓存；
- `src/bench_attention.cu`：固定大形状的独立测速入口。

关键数值细节：

```cpp
const float scale = 1.0f / sqrtf(static_cast<float>(head_dim));
const float exp_value = expf_parts(dot * scale - row_max, exp_scale);
const float p = exp_value * exp_scale;
```

先算 `dot * scale` 再取最大值，最后做 `exp`；不能把顺序换成先 `exp` 再缩放，否则 float 结果会和参考实现出现末位差异。

## 5. 官方测试结果

测试命令：

```bash
SKIP_RMS_NORM=1 ./test_kernels --verbose
```

结果：**28 / 28 Passed**，覆盖 14 个形状 × `float/half` 两种精度；所有用例 `Max Diff = 0.0000000`。

最大形状 `B=4, T=512, S=2048, Hq=64, Hkv=64, D=32, causal=1`：

| 精度 | 平均耗时 | 最大误差 |
|---|---:|---:|
| float | 137.73 ms | 0 |
| half | 106.73 ms | 0 |

独立 benchmark（同一形状，3 次均值，包含 H2D/D2H）为 **137.40 ms**。

## 6. Nsight Compute（中文解读）

采集条件：RTX 3080（CC 8.6），单次 kernel，float，上述最大形状。

| 指标 | 实测 | 中文含义 |
|---|---:|---|
| Duration | 143.60 ms | 单次 kernel 执行时间 |
| Compute (SM) Throughput | 39.78% | SM 计算吞吐只有峰值的约四成 |
| Memory Throughput | 39.78% | 内存管线吞吐同样约四成 |
| DRAM Throughput | 0.07% | 几乎不直接打 DRAM，数据主要命中 L1/L2 |
| L1/TEX Hit Rate | 94.74% | L1 命中率很高 |
| L2 Hit Rate | 98.63% | L2 命中率很高 |
| Achieved Occupancy | 81.56% | 理论占用率 83.33%，实际接近理论值 |
| Registers Per Thread | 44 | 每线程 44 个寄存器 |
| Average Active Threads/Warp | 1.90 | 每个 warp 平均只有 1.9 个线程真正干活 |
| Warp Cycles Per Issued Instruction | 48.72 | 发射一条指令平均等 48.7 个周期 |

NCU 的结论很明确：** occupancy 不低，但有效并行度极低**。一个 block 的 256 个线程里，计算 score 时只有 0 号线程在工作，其余线程在 barrier 等待。报告给出的“约 87.1% 周期耗在 CTA barrier”与源码完全对应。

## 7. Nsight Systems（中文解读）

采集 6 次 kernel（1 次预热 + 5 次计时）：

| 项目 | 数值 | 中文含义 |
|---|---:|---|
| kernel 实例数 | 6 | 6 次 `flash_attention_v1_kernel<float>` |
| kernel 平均时间 | 109.83 ms | GPU 上 kernel 本身的均值 |
| kernel 中位数 | 105.39 ms | 中位数 |
| kernel 最短 / 最长 | 105.24 / 121.64 ms | 波动范围 |
| 18 次 H2D 拷贝 | 平均 10.50 ms | 每次调用拷 Q/K/V 到显存 |
| 6 次 D2H 拷贝 | 平均 3.27 ms | 每次调用拷回输出 |

Nsight Systems 说明端到端时间不只是 kernel：每次调用还要做三次 H2D 和一次 D2H。V1 的 kernel 占绝对主导，优化空间首先在 kernel 内部，而不是拷贝。

## 8. 评价

**优点**

- 数值与参考实现完全对齐，float/half 全部零误差；
- 逻辑直观，适合作为调试和回归基线；
- 暴露出的瓶颈非常明确，便于后续版本逐项对照。

**缺点**

- 一个 block 只有一个线程计算 score，GPU 并行度被严重浪费；
- 每个 query 行都重复读取整行 K/V，全局访问量大；
- 中间 `score` 需要整行共享内存，`S=2048` 时占用明显；
- 大形状耗时 137.7 ms，离可用性能很远。

**结论**：V1 是“正确性锚点”，不作为最终性能版本。
